# 2. Lý do phải thực hiện ở Phase 0

Ví dụ:

- Không có mục tiêu tải nhưng thêm Redis từ đầu.

- “Hệ thống phải nhanh.”

# 5. Performance Requirements

## 5.1. Response Time Targets

Trong môi trường gần production, với tải thông thường:

| Loại API | Mục tiêu p95 |
|---|---:|
| Health endpoint | ≤ 200 ms |
| Public product list/detail | ≤ 500 ms |
| Cart operations | ≤ 500 ms |
| Profile/address operations | ≤ 500 ms |
| Admin CRUD thông thường | ≤ 800 ms |
| Checkout validation | ≤ 1.500 ms |
| Create Order COD | ≤ 2.000 ms |
| Reporting cơ bản | ≤ 3.000 ms |

Các mục tiêu trên không bao gồm thời gian của external provider chưa được kiểm soát.

## 5.2. Database Performance

- Query chính phải dùng index phù hợp.
- Không chấp nhận N+1 trên API quan trọng.
- Pagination bắt buộc cho collection lớn.
- Không load toàn bộ Catalog, Order hoặc User vào memory.
- Không dùng wildcard search không kiểm soát trên dữ liệu lớn.
- Reporting không được khóa hoặc làm chậm luồng Checkout.
- Query chậm phải có khả năng nhận diện qua log hoặc metrics.

## 5.3. Payload Limits

Baseline đề xuất:

- Request JSON thông thường phải có giới hạn hợp lý.
- Page size mặc định: 20.
- Page size tối đa: 100.
- Cart item quantity phải có giới hạn.
- File upload không được phép không giới hạn.
- Product image upload phải có giới hạn số lượng và kích thước.

Giá trị chính xác của upload limit vẫn là open decision.

## 5.4. Không tối ưu sớm

Không được thêm mặc định:

- Redis.
- Elasticsearch.
- Distributed cache.
- Read replica.
- Message queue.

Chỉ bổ sung khi có bằng chứng:

- Query chậm.
- Tải vượt khả năng hiện tại.
- Cache mang lại lợi ích đo được.
- MySQL search không còn đáp ứng.

# 6. Security Requirements

## 6.1. Authentication

- Password phải được hash bằng thuật toán phù hợp.
- Không lưu password plain text.
- JWT phải được verify đầy đủ.
- Token hết hạn không được chấp nhận.
- Refresh Token phải có lifecycle riêng.
- Refresh Token không được lưu plain text nếu có thể lưu hash.
- User `DISABLED` hoặc `LOCKED` không được tạo session mới.
- Authentication error không được làm lộ quá nhiều thông tin.

## 6.2. Authorization

- Mọi protected endpoint phải kiểm tra authorization phía Backend.
- Frontend ẩn nút không phải là security control.
- Identity phải lấy từ Security Context.
- Không dùng `userId` trong request làm nguồn identity cuối cùng.
- Mọi resource cá nhân phải kiểm tra ownership.
- Staff/Admin vẫn phải tuân theo business rules.
- Không hỗ trợ mass assignment.

## 6.3. Input Security

- Bean Validation phía Backend là bắt buộc.
- Request phải giới hạn kích thước.
- Không bind request trực tiếp vào JPA Entity.
- Không dùng raw SQL ghép chuỗi.
- File upload phải kiểm tra type, size và ownership.
- Không tin MIME type chỉ từ client.
- Webhook phải verify signature.
- External ID phải được validate.

## 6.4. Secrets

Không được commit:

- Database password.
- JWT secret/private key.
- Payment provider secret.
- Email credentials.
- Object storage credentials.
- Production environment file.

Secrets phải được cung cấp qua:

- Environment variables.
- Secret management của platform deploy.
- Local `.env` không commit.

## 6.5. Sensitive Logging

Không log:

- Password.
- Password hash.
- Access Token.
- Refresh Token.
- Reset password token.
- Email verification token.
- Payment credentials.
- Full webhook secret.
- Database password.

Dữ liệu cá nhân phải được hạn chế trong log:

- Email có thể mask khi phù hợp.
- Phone và address không log toàn bộ nếu không cần.
- Không log toàn bộ request body mặc định.

## 6.6. Security Headers và Transport

Production phải:

- Sử dụng HTTPS.
- Thiết lập CORS rõ ràng.
- Không dùng wildcard origin cùng credentials.
- Có security headers phù hợp.
- Không expose debug/error detail ra client.
- Không expose Actuator nhạy cảm công khai.

## 6.7. Abuse Protection

MVP cần cân nhắc rate limiting cho:

- Login.
- Register.
- Refresh Token.
- Forgot password.
- Reset password.
- Public search nếu bị abuse.
- Webhook nếu provider contract cho phép.

Rate limiting phân tán chưa bắt buộc khi chỉ deploy một instance.

# 7. Reliability Requirements

## 7.1. Transaction Correctness

Các flow quan trọng phải có transaction boundary rõ:

- Register.
- Inventory adjustment.
- Checkout.
- Create Order.
- Cancel Order.
- Restore Stock.
- Coupon usage.
- Payment transition.
- Shipment transition.

Nếu transaction thất bại:

- Không được để partial state không hợp lệ.
- Không được trừ Stock mà không có Order hợp lệ.
- Không được restore Stock nhiều lần.
- Không được ghi Payment `PAID` một phần.

## 7.2. Idempotency

Các operation sau phải có chiến lược idempotency:

- Create Order khi client retry.
- Payment webhook.
- Shipping webhook.
- Restore Stock.
- Refund.
- Coupon usage khi retry.
- External event processing.

## 7.3. Concurrency

Hệ thống phải bảo vệ:

- Sản phẩm cuối cùng bị hai Customer mua cùng lúc.
- Coupon usage slot cuối cùng.
- Hai Staff confirm cùng một Order.
- Cancel và confirm xảy ra đồng thời.
- Duplicate webhook.
- Concurrent inventory adjustment.

## 7.4. External Dependency Failure

Khi external provider lỗi:

- Có timeout.
- Không chờ vô hạn.
- Không retry không giới hạn.
- Không retry operation không idempotent một cách mù quáng.
- Lỗi provider không được làm mất internal state.
- Có khả năng reconciliation khi cần.
- Provider failure phải được log có correlation.

## 7.5. Graceful Failure

API lỗi phải:

- Trả error code ổn định.
- Không lộ stack trace.
- Không lộ SQL.
- Không lộ secret.
- Có correlation ID.
- Phân biệt lỗi validation, authentication, authorization, business và system.

# 8. Availability Requirements

## 8.1. Availability Target

Baseline đề xuất cho dự án cá nhân/cửa hàng nhỏ:

- **Availability target: 99% theo tháng.**
- Không cam kết high availability cấp enterprise.
- Maintenance có kế hoạch được chấp nhận.

99% tương đương hơn 7 giờ downtime mỗi tháng. Đây là target thực tế hơn so với tuyên bố 99,99% khi chỉ có một instance và một database.

## 8.2. Health Endpoints

Cần có:

- Liveness.
- Readiness.
- Database connectivity health.
- Application version/build information ở mức an toàn.

Không public:

- Full environment.
- Secrets.
- Internal configuration.
- Sensitive Actuator endpoints.

## 8.3. Graceful Shutdown

Ứng dụng phải:

- Ngừng nhận request mới.
- Cho request đang xử lý hoàn tất trong giới hạn phù hợp.
- Đóng connection pool đúng cách.
- Không làm hỏng transaction đang chạy.

# 9. Scalability Requirements

## 9.1. MVP Scalability

Hệ thống phải có khả năng:

- Chạy một instance ban đầu.
- Có thể chạy nhiều instance sau này mà không dựa vào memory cục bộ cho business correctness.
- Không dùng `synchronized` như giải pháp duy nhất cho Inventory concurrency.
- Không lưu session server-side bắt buộc nếu dùng JWT.
- Không lưu state quan trọng chỉ trong application memory.

## 9.2. Vertical Scaling trước

Thứ tự ưu tiên:

1. Tối ưu query.
2. Bổ sung index.
3. Điều chỉnh connection pool.
4. Tăng tài nguyên instance.
5. Scale nhiều instance khi thực sự cần.
6. Chỉ bổ sung distributed component khi có bằng chứng.

## 9.3. Stateless API

REST API nên stateless ở mức phù hợp:

- Request độc lập.
- Identity từ token.
- Business state trong database.
- Không phụ thuộc sticky session.

Refresh Token vẫn là persisted security state và không mâu thuẫn với nguyên tắc này.

# 10. Data Integrity Requirements

## 10.1. Database as Final Integrity Layer

Phải sử dụng khi phù hợp:

- Primary key.
- Foreign key.
- Unique constraint.
- Check constraint.
- Not null.
- Optimistic locking/version.
- Index.
- Transaction.

## 10.2. Money

- Dùng `BigDecimal` trong Java.
- Dùng `DECIMAL` trong MySQL.
- Không dùng `float` hoặc `double`.
- Có rounding policy rõ.
- Currency của Order và Payment phải nhất quán.

## 10.3. Snapshot

Order phải lưu snapshot tối thiểu:

- Product name.
- Variant/SKU.
- Size.
- Color.
- Unit price.
- Discount.
- Quantity.
- Line total.
- Shipping address.
- Shipping fee.
- Coupon result khi áp dụng.

Không phụ thuộc Catalog hiện tại để tái tạo sự thật lịch sử của Order.

## 10.4. Audit Fields

Các dữ liệu mutable quan trọng nên có:

- Created at.
- Created by khi phù hợp.
- Updated at.
- Updated by khi phù hợp.
- Version.

Các bảng lịch sử/event cần giữ sự thật nghiệp vụ và không được sửa tùy ý.

## 10.5. Delete Policy

Không hard delete:

- Order.
- Order Item.
- Payment.
- Shipment history.
- Inventory history.
- Coupon usage.
- Product/Variant đã được Order tham chiếu.

# 11. Logging Requirements

## 11.1. Mức log

- `ERROR`: lỗi hệ thống hoặc failure nghiêm trọng cần điều tra.
- `WARN`: hành vi bất thường nhưng request có thể xử lý.
- `INFO`: lifecycle quan trọng và operation summary.
- `DEBUG`: chỉ bật ở môi trường phát triển hoặc điều tra có kiểm soát.
- Không dùng `TRACE` mặc định ở Production.

## 11.2. Correlation

Mỗi request phải có:

- Correlation ID.
- Request ID khi cần.
- Actor ID khi đã xác thực và an toàn.
- Operation name.
- Result/status.
- Duration.

Các external calls nên truyền hoặc liên kết correlation ID khi provider hỗ trợ.

## 11.3. Business Events cần log

Tối thiểu:

- Login failure ở mức an toàn.
- Account disable/enable.
- Inventory adjustment.
- Order created.
- Order cancelled.
- Stock restored.
- Payment transition.
- Webhook rejected.
- Shipment transition.
- Admin-sensitive actions.

Logging không thay thế audit trail persisted.

# 13. Backup và Recovery Requirements

## 13.1. Backup

Production hoặc demo có dữ liệu thật phải có:

- Automated database backup.
- Backup định kỳ.
- Retention policy.
- Backup nằm ngoài container volume chính.
- Không chỉ copy application JAR.

## 13.2. Restore

Backup chỉ được coi là hợp lệ khi đã restore thử.

Phải có:

- Restore procedure.
- Kiểm tra migration compatibility.
- Kiểm tra dữ liệu sau restore.
- Runbook.

## 13.3. RPO và RTO sơ bộ

Baseline đề xuất:

- **RPO: tối đa 24 giờ.**
- **RTO: tối đa 4 giờ.**

Ý nghĩa:

- Có thể mất tối đa dữ liệu từ lần backup gần nhất trong 24 giờ.
- Mục tiêu khôi phục dịch vụ trong vòng 4 giờ.

## 13.4. Hạn chế

RPO 24 giờ có thể quá yếu nếu hệ thống nhận đơn thật.

Khi chuyển từ portfolio/demo sang vận hành thật, cần xem xét:

- Backup thường xuyên hơn.
- Binary log hoặc point-in-time recovery.
- Kiểm thử restore định kỳ.
- Giảm RPO.

# 14. Maintainability Requirements

## 14.1. Architecture

- Tuân thủ Module Boundaries Phase 0.7.
- Không circular dependency.
- Không module truy cập Repository module khác.
- Không Shared business logic.
- Không generic CRUD abstraction không cần thiết.
- Không để Controller chứa business logic.

## 14.2. Code Quality

- Tên class/method thể hiện nghiệp vụ.
- Method giữ phạm vi trách nhiệm hợp lý.
- Không hardcode business rule.
- Không magic number không giải thích.
- Không duplicate logic quan trọng.
- Exception có ý nghĩa và error code ổn định.

## 14.3. Documentation

Phải duy trì:

- README.
- ADR.
- Phase baselines.
- ERD sau này.
- API documentation.
- Deployment runbook.
- Backup/restore runbook.
- Environment configuration guide.

## 14.4. Dependency Governance

- Không thêm library nếu JDK/Spring đã đáp ứng tốt.
- Không pin Spring Framework version thủ công.
- Dependency ngoài Spring Boot BOM phải được kiểm tra tương thích.
- Có kiểm tra vulnerability.
- Không dùng dependency không còn duy trì nếu có lựa chọn phù hợp hơn.

# 16. Deployment Requirements

## 16.1. Build

- Build bằng Maven Wrapper.
- Build từ clean checkout.
- Packaging JAR.
- UTF-8.
- Không phụ thuộc IntelliJ.

## 16.2. Docker

- Multi-stage build khi phù hợp.
- Runtime image tối giản.
- Container chạy non-root.
- Không chứa secret.
- Có health check.
- Có graceful shutdown.

## 16.3. Configuration

Tách:

- Local.
- Test.
- Production.

Production config:

- Không dùng default password.
- Không bật SQL log nhạy cảm.
- Không bật debug.
- Không tự tạo schema bằng Hibernate.
- Flyway chịu trách nhiệm migration.

## 16.4. CI

# 21. NFR Decisions đã khóa

## 21.1. Performance

- Có response time target cấp API.
- Pagination bắt buộc cho collection lớn.
- Không chấp nhận N+1 ở flow chính.
- Không thêm cache/search infrastructure khi chưa có evidence.

## 21.2. Security

- Backend không tin client.
- Secret không nằm trong Git.
- Không log credential/token.
- Authorization và ownership bắt buộc.
- Production dùng HTTPS.

## 21.3. Reliability

- Critical flow phải transaction-safe.
- Webhook và retry phải idempotent.
- Concurrency không được tạo side effect lặp.
- External call phải có timeout.

## 21.4. Availability

- Baseline availability là 99%.
- Không tuyên bố enterprise HA.
- Có liveness/readiness.
- Có graceful shutdown.

## 21.5. Data

- MySQL constraints và Flyway là bắt buộc.
- Order dùng snapshot.
- Không hard delete history nghiệp vụ.
- Tiền dùng BigDecimal/DECIMAL.

## 21.6. Observability

- Có correlation ID.
- Có structured logging ở mức phù hợp.
- Có basic metrics và health check.
- Không log PII/secret quá mức.

## 21.7. Recovery

- Backup tự động.
- Restore phải được test.
- RPO/RTO sơ bộ được ghi nhận.

## 21.8. Quality

- Unit, integration, security, architecture và concurrency test.
- Build từ clean checkout.
- CI không được bỏ qua test trọng yếu.
